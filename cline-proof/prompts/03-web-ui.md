A. Server-side SSE filtering (most important). The agent_text and reasoning events are unguarded model output and have leaked fixes (for example the corrected division for the average) to the browser. Fix this on the server, not just in the UI: GET /api/session/:id/stream must never send agent_text or reasoning events (and must not put model free text into any other event either, including tool_call/tool_result payloads of give_hint attempts that the guard rejected). Use an explicit allow-list of event types that may go to the client: test_results, tool_call (only for run_commands/read_files, with command or file name), tool_result (for run_commands: a short trimmed output summary; never the model's own text), approval (allowed/denied + command), hint (accepted, guarded hints only), hint_status/hint_rejected (no rejected text, just the reason category), status, error (friendly message only, see B), done. Keep the full raw events server-side only (for logs/debugging) if you want, but never stream them. Apply the same filter to the replay of past events.

B. Friendly errors. Turn raw error events into short human lines before they are sent, for example "Command blocked by allow-list: <command>", "Hint blocked: contained code, asking the tutor to rephrase", "Hint blocked: wrong level, asking the tutor to retry", "Tutor timed out, try again". No stack traces or raw SDK messages in the browser.

C. Web UI in web/ (plain HTML + CSS + vanilla JS, no build step, served by Express as static files at /). Clean, demo-ready on a projector: large readable fonts (base 18px+), high contrast, generous spacing, a simple header "HintLab: a debugging tutor that never writes the fix". Layout:
  1. Assignment picker (from GET /api/assignments) showing the statement and language; choosing one preloads its buggy starter code into an editable monospace textarea.
  2. "Run & get hint" button -> POST /api/session { assignmentId, code }; show the test results table (test name, input, expected, got, PASS/FAIL with colour, plus timeout/signal/build error info if present) from testResults.
  3. Live feed from GET /api/session/:id/stream (EventSource): only tool calls (the commands the tutor ran and their short results), test results, approvals and denials, hints and friendly status/error lines. Each item one short line with a small icon or label. Auto-scroll.
  4. Hint cards labelled "Level 1: nudge", "Level 2: where to look", "Level 3: the concept", appearing as each hint arrives. Hint text must be inserted with textContent (never innerHTML).
  5. Loading states: a spinner/"Tutor is reading your code..." while waiting for the first hint (typically 10-13 s), and "Thinking about the next hint..." after "Next hint" (typically 5-9 s). Disable the Next hint button while busy; if the server returns 409 show "Tutor is still busy, please wait" and keep the button disabled until the next hint/status arrives. After level 3 show "All hints given" and keep the button disabled. Starting a new run closes the old EventSource and resets the cards.
  6. Handle server errors (400/404/network) with a visible friendly message.

D. Smaller guard fixes (examples below are described in words on purpose; turn them into your own test strings):
  - Hint guard (src/hintGuard.ts): also block hints that embed a one-line code expression inside prose, with or without backticks. Examples the tester saw or expects: comparing a cleaned string variable for equality against its reversed slice; a range call that starts at one and ends at the length of the nums list; the sum variable divided by n; indexing nums with i; reversing s with a slice; and a C-style float cast of sum divided by n. In general: identifiers combined with code syntax such as call parentheses, square-bracket indexing or slicing, comparison or arithmetic operators between identifiers, casts, or semicolons. Stop the false positive on plain English prose such as the phrase "for x in the list" or "if the list is empty": programming keywords on their own are not code; only flag them when real code syntax is present. Add unit tests in scripts/check-agent.ts for both the new blocked cases and the prose that must pass.
  - Allow-list (src/allowlist.ts): deny any dollar sign anywhere in a command (variable or command expansion, for example echoing the HOME variable into the Python program), and remove the echo/printf pipe forms entirely so that no command containing a pipe character is allowed. Instead, when creating the agent workdir, write each test's input to its own file (named input-<test-name>.txt with a safe slug) and tell the agent in its prompt to feed those files to the program with a stdin redirect from that file name. Keep the other allowed forms: running python3 on main.py, the exact gcc build command from tests.json, running ./main, the stdin redirect from an input-*.txt file in the workdir, and cat of main.py, main.c, tests.json or an input-*.txt file. Update the allow-list unit tests so that echoing the HOME variable piped into the program, echoing a literal number piped into the program, a stdin redirect from a dollar-sign variable, and any other pipe are all denied.
